# 漢字校正と議事録の担当者照合

検証日: 2026-11-19

今回、文脈付きの修正例を保存・利用する機能と、議事録の人名を原文の引用で確かめる検査を追加した。yomiyasuの意味保持と読みやすさの原則も議事録・要約の生成に組み込んだ。文字起こしはWhisper、校正・議事録はローカルgemma4という構成を維持している。

## 問題と実装

相談で挙がったのは「架電」が「家電」、「監査ログ」が「カーサログ」になる誤変換と、議事録で共同担当者が別の組に変わる問題だった。後者は文字起こしが正しくても起きるため、本文の校正と議事録の照合でそれぞれ対処した。

以前の修正学習は差分を語句として取り出していた。「家電→架電」の差分は「家→架」になり、1文字の修正を除外する条件にかかっていた。一方、同音異義語を無条件で置き換えると「家電製品」まで誤る。そのため新しい参考例には修正前・修正後・適用場面を保存する。短い発言の手修正も発言全体で記録し、現在の校正区間と近い最大12例・合計2000文字を渡す。

AI校正は赤字以外も対象にし、採用した変更箇所をすべて赤字にする。数字、登録済みの人物、特定の否定・未確定表現を変更する回答は原文のまま保留する。登録された別名を正式名に直すことは許可する。この検査は全ての意味変更を検出するものではない。

議事録の照合には、人物辞書や背景メモを事実の根拠として渡さない。人名を含む項目の判定時に、発言の時刻と引用を要求する。登録済みの人物・話者について、引用がその時刻の発言本文に実在するか、人物と内容語が対応するかを調べる。話者名だけを担当の根拠にせず、共同担当者の欠落も保留する。回答漏れ・重複回答・採用できない修正・引用不足は「要確認：原文との照合未完了」と表示する。引用と判定は会議フォルダの `documents.json` に記録する。

## yomiyasuの導入範囲

エージェント用のyomiyasuスキルはインストール済みだった。アプリには連携がなかったため、今回、意味・条件・数値・固有名詞・確度を保って読みやすくする原則を生成指示へ追加した。議事録の担当者の組を保持する指示も含めた。

生成後の全文書き換えを別途挟まず、既存の生成処理で適用してから原文と照合する。発言本文はこの文章整理の対象外。上流のCLI・lint・意味検査フロー一式を組み込んだものではなく、アプリ向けの指示として採用している。

参照元は [nanaism/yomiyasu](https://github.com/nanaism/yomiyasu/tree/c9b9a6d1bb0795356c0e34dc50f501424069d837)。MITライセンスと出典は `third_party/yomiyasu/` に保存した。`llm.yomiyasu: false` で生成指示への追加を無効化できる。

## 検証結果

自動テストは既存127件に14件を追加し、全141件が通った。1文字修正の保存、同音異義語、人物・数値・否定の変更拒否、赤字の保持、虚偽の引用、違う時刻、返答漏れ、共同担当の欠落、別の仕事の引用、文書への警告と判定記録の保存を確認した。

一度、実モデルと検証サーバーを保持した状態の実行で、Windowsのページングファイル不足により既存の音声系テスト3件が失敗した。検証用モデルを解放し、検証サーバーを停止した後の全件実行は成功した。関連のないアプリやユーザーの7860番ポートは停止していない。

実際のローカルモデル `hf.co/unsloth/gemma-4-31B-it-GGUF:UD-IQ3_XXS` でも、次の短い合成例を試した。12Bへの切り替えは発生しなかった。

| 「家電製品」は変更しない | 成功 | 成功 |
| 設定変更の「カーサログ」を「監査ログ」に直す | 成功 | 成功 |

旧版も全て正解しているため、この小規模な試験から認識率の向上は主張できない。上表は旧処理コードと同じ版（`a3e60c4`）のプロンプトを指定して比較した結果。改修後は校正5発言のうち2発言を変更し、担当者1項目を引用付きで修正した。所要時間は旧処理19.0秒・改修後13.1秒だったが、モデルの読み込みやキャッシュ、実行順が異なるため速度比較には使わない。

ブラウザでは、個人データを含まない7870番ポートの検証画面で文脈付きヒントを編集し、保存通知と再読み込み後の値を確認した。ユーザー設定とは分離した保存先を使用した。

検証データの保存先は `output/20261119_漢字と担当者の検証/`。上表の結果は `同版プロンプト比較/results.json` にある。初回の `results.json` は旧処理コードにも新しいプロンプトを読み込んだ参考試験で、旧版との比較には使わない。`final/results.json` は改修後だけの再確認。各回のMarkdownと文脈付きヒント、UI検証用データも保存した。これらはGit管理外。再現用の `tools/try_text_accuracy.py` は新しい出力先を必須にし、人物・用語・参考例を検証用データへ差し替えて実行する。旧処理との比較時には `--baseline` と `--baseline-prompts` の両方を指定する。

このPCでは既存辞書を同フォルダの `辞書変更前/` にバックアップし、「架電」「監査ログ」の用語と適用場面を登録した。「家電→架電」の無条件置換は登録していない。

## 利用手順と残る課題

アプリを再起動した後、「用語辞書」の文脈付きヒントを確認する。保存済み会議にも適用する場合は、「修正」のAI校正で「すべての発言」を選ぶ。校正済みの発言には「校正済みもやり直す」を使う。赤字と保留を聞き直して保存し、照合をONにして議事録を作り直す。

今回は実録音のWhisper再実行をしていない。音が曖昧な区間の正解を文章だけで確定することはできず、未知の人名や複雑な役割関係も検査で見逃し得る。内容語が一致しない正しい言い換えは保留が増える可能性があり、逆に同じ語を使う別の仕事は区別できない場合がある。原文の時刻付近から選ぶ範囲は従来どおり±75秒・最大1400文字なので、必要な根拠がその外にある場合にも確認が必要になる。

次は実録音から正解文を作り、誤変換を直せた割合に加え、正しかった表記を変えてしまった割合を測る。議事録は「誰が・何を・誰と・いつまでに」の組を原文と照合して評価する。例文での成功と、実会議での品質改善は分けて判断する。
