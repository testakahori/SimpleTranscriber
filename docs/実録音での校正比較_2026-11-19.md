# 実録音での校正と議事録の比較

2026-11-19。会議_7.m4aの保存済みWhisper本文を使い、改修前後の校正と議事録処理を比較した。実データを含む詳細はローカルの `output/20261119_会議7_実録音比較/` に保存する。本書には会議本文・人物辞書・接続情報を掲載しない。

## 比較条件と評価の限界

音声は62分13.815秒、保存済み本文は210発言・14,116文字。元音声のハッシュが以前の全編実験の記録と一致することを確認した。今回の変更対象である校正・議事録処理の差を見るため、両群へ同じWhisper結果を渡した。音声認識と話者識別は再実行していない。

旧処理は `a3e60c4`、改修後は `4ed3789` の `core/minutes.py` と同じ版のプロンプト・テンプレートを使用した。補助モジュールは共通の現在の版を使用した。人物・用語辞書、会議メモ、温度0.1、seed 42を固定。比較用ツールは `tools/compare_saved_meeting.py`。途中結果・モデルへの入力と返答・版情報を保存し、既存の会議ファイルを上書きしない。

標準のgemma4 31Bはメモリ不足で起動できなかった。画像用部品を外した31Bも失敗したため、両群ともインストール済みgemma4 12Bの同じテキスト重みとテンプレートを使った。画像用部品を外した実験用モデルを別名で作成し、バッチ数64・別モデルへの自動切り替えなしで実行した。アプリ設定と他の稼働サービスは変更していない。実験用モデルの作成は [Ollama公式のGGUFインポート手順](https://docs.ollama.com/import)に従った。

この環境は音声の直接聴取に対応していない。漢字は前後の文脈からの暫定判定、担当は保存済み発言との整合性の評価である。音声と照合した正解文に対する文字誤り率ではなく、31Bの品質を評価した結果でもない。

両群の全210発言の校正、議事録生成、原文照合まで完了した。各群1回ずつの比較であり、応答の揺れは未測定。議事録には各群で校正した本文を渡しているため、議事録だけの変更を切り分けた試験ではない。

## 漢字・用語は改善を確認できなかった

校正結果を見る前に、文脈から誤変換を疑える23項目を選んだ。無作為抽出ではなく、全編の正答率を表す数値ではない。

| 指標 | 旧処理 | 改修後 |
|---|---:|---:|
| 校正済みの発言 | 210 | 209 |
| 保留した発言 | 0 | 1 |
| 本文を変更した発言（句読点を含む） | 50 | 49 |
| 23項目のうち期待表記になった | 4 | 0 |
| 誤変換候補が残った | 16 | 23 |
| 期待表記と異なる別表現になった | 3 | 0 |

旧処理は「公欠」「打刻時刻」「授業日数」に関する4項目を修正した。改修後はその4項目を含め全23項目の候補が残った。旧処理の別表現3項目には、別の誤った表記が2件、誤人名を除いて意味の通る表現になったものが1件ある。事前に定めた期待表記とは別枠にした。

改修後の23項目は保護検査に拒否されたわけではなく、モデルの返答が誤変換候補を残していた。プロンプトへの注意書き追加だけで、長い実録音由来の入力に対する校正が改善するとは確認できなかった。

保留した1発言は、校正案が元の数字を一つ落としていたためで、数字を守る検査は働いた。誤変換を直す効果と、誤った校正を止める効果は分けて評価する。

## 担当者の取り違えの減少も示せなかった

旧処理のアクション3行、改修後の2行と、事前に選んだ10項目の役割説明を点検した。確認したアクション行では、明確な別人への取り違えは両群とも0件。ただし旧処理でも発生しなかったため、減少の証拠にはならない。説明会の操作上の役割は、会議後の実行タスクと区別して評価した。

旧処理に残った確認事項が、改修後には議事録全体から抜けた例があった。旧処理ではその事項に誤った「確認できず」の警告が付いた。呼び出し記録を見ると、時刻のない項目に対して担当者名だけが一致した序盤の発言が選ばれ、該当する発言が照合へ渡っていなかった。担当名が合うかだけでなく、約束や確認事項が残るか、根拠を正しく選べるかの評価が必要。

マニュアルの案内や条件付きのフィードバック依頼を、一律のタスクとしてまとめる例も両群に残った。改修後では操作説明を新しい確認タスクに変えた可能性がある行に、「確認できず」が付いた。

改修後の照合対象50項目の内訳は、採用8・修正1・確認できず6・要確認35だった。内部の `checked=49` は一意な判定を受け取った件数であり、確認成功数ではない。1項目は番号が重複していた。

9回の照合応答に時刻付きの根拠引用は0行。要確認35件のうち31件は人物を含み、引用がないため確定できなかった。保存済みの発言者と内容が合う説明にも要確認が付いたので、35件を誤り検出数とは扱えない。プロンプトにある「1行だけ」と「次の行に根拠を出す」という指示の併記、報告者と実行担当者の扱い、短い人名の部分一致を見直す必要がある。

## 追加診断では短い入力と適切なヒントが役立った

本比較後に既知の3発言を1発言ずつ渡し、同じモデルと設定で試した。ヒントを追加する条件では、対象の誤表記・正表記・適用場面だけをメモリ上に追加し、実際の辞書は変更していない。

|対象|1発言ずつ・既存ヒント|1発言ずつ・対象に合ったヒント追加|
|---|---|---|
|三田国 → 未打刻|誤りが残る|修正を採用|
|過電 → 架電|修正を採用|修正を採用|
|次元 → 時限|案では修正されたが、別の数字を落とし発言全体を保留|数字を保持した修正を採用|

対象語の修正を採用できたのは1/3から3/3になった。ただし、既知の誤りに合わせた診断であり、汎用的な精度向上の証拠ではない。事前に選んだ23項目の結果とは混ぜない。入力を短くすることと、適切な用語ヒントを選ぶことを次の検証候補とする。

## 後処理で作られた誤人名

認識単語には正しく残っていた一般語が、人物名統一の後で実名に変わった箇所を2件確認した。現在の人物名統一処理へ通常の文を渡しても同じ問題を再現できた。人名の別名を文字列の一部として無条件に置き換えていたことが原因である。

また、短いひらがな名を一般語の一部分から検出する例がある。人物名の保護・照合でこの一致を実在の人物への言及と扱うと、誤警告や校正の過剰な保留につながる。名前を含むかどうかの単純な文字列一致を、担当の正しさの判定にそのまま使わないことが必要。

## 議事録生成中に確認した問題

校正後の本文は旧処理14,284文字・改修後14,253文字だが、赤字表示用のHTMLタグを含めると31,117文字・35,860文字になった。入力長の見積もりにより、約1時間の会議でも区間メモによる圧縮が発生した。

旧処理の最初のメモ生成は入力17,313トークンに対して出力14,929トークン・32,696文字で、ほとんど短くならなかった。次のメモも34,101文字になり、コンテキスト長による終了だった。出力予約は呼び出しの入力予算を計算する値で、生成する長さの上限にはなっていない。中間メモをさらに処理するため時間が増える。表示用タグをLLM入力から分離し、中間メモの長さ・圧縮率・打ち切りを検査する必要がある。

|段階|旧処理|改修後|
|---|---:|---:|
|全210発言の校正|257.4秒|264.9秒|
|議事録生成と原文照合|852.9秒|310.3秒|

別フォルダの起動失敗試行はこの時間に含まない。完了した比較でもメモリ不足が2回発生したが、同じモデルへの再試行で回復した。両群とも別モデルへの切り替え、未実行バッチ、最終エラーはなし。単発の測定なので、一般的な高速化の証拠にはしない。

## 記録と次の検証

詳細レポート、23項目の比較一覧、担当・役割の比較、音声付きHTML、新旧の本文と議事録、21発言の聞き直し用MP3、追加診断、失敗した起動試行をローカル出力先に保持した。元の文字起こしが変わっていないことをハッシュで確認し、結果ファイルのハッシュ一覧も保存した。実データはGit管理外。

次の改善候補は、一般語を人物名へ変えてしまう表記統一の修正、校正入力の分量と用語ヒントの選び方、担当関係を含む根拠の検索と引用形式、表示用タグと生成用本文の分離である。手を加えた評価用例の成功を一般的な精度改善とは扱わず、未使用の録音でも確認する必要がある。

今回の変更は比較用ツールと検証記録であり、アプリ本体の上記の不具合はまだ修正していない。31Bでの比較と、音声を聞き直した正解文による評価は残る。
