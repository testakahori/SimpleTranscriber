# 新しいPCで使い始める手順

1. Python 3.12 と ffmpeg を入れ、`run.bat` を実行（venv作成、NVIDIA GPUがあればCUDA版PyTorch、依存パッケージを自動導入）
2. Ollama を入れて `ollama pull hf.co/unsloth/gemma-4-31B-it-GGUF:UD-IQ3_XXS`（約11GB）
3. 高精度な話者分離を使う場合: Hugging Face で `pyannote/speaker-diarization-community-1` と `pyannote/segmentation-3.0` の利用規約に同意 → Readトークンを発行 → 設定タブに入力
4. 人物・声紋タブで参加者の声紋を登録（10〜30秒の本人だけの音声）

# 設計判断ログ

## 第2次（2026-09-27〜28）
- **議事録書式**: ユーザー提供の参考議事録（実名入りのためリポジトリ外・コミット禁止）に準拠。【会議概要】【要点サマリー】【議題別の詳細】【決定事項】【アクションアイテム】（表）【保留・検討事項】【AIの意見】。「AIの意見」は議事録を作ったAI自身の所見（ユーザー指示）
- **LLM**: ユーザー指定は「gemma4の一番強いやつ」＝31B。Q4版(21.5GB)は16GB VRAMに載らずCPUに溢れて2.5 tok/s、さらにOllama 0.34.4ではGPU/CPU分割ロードがCUDAエラーで起動しなくなった。→ `hf.co/unsloth/gemma-4-31B-it-GGUF:UD-IQ3_XXS`（11GB）+ `ollama_num_gpu: 99`（Ollamaの自動見積もりは控えめで一部をCPUに逃がすため強制）で全層GPU、25 tok/s。品質はQ4版とほぼ同等を実測
- **3bit版の癖**: 校正で文脈に合わない文を丸ごと消すことがある → `_drops_content` で6文字以上の削除を含む校正は不採用（フィラー削除は許可）
- **話者分離**: 固定しきい値の階層クラスタリングは合成音声では完璧だったが、実会議（4h・発言中央値1.1秒）で707人に崩壊。→ 窓を3つずつ平均した約3秒の声紋で、NME-SC（近傍数pを振って固有値ギャップ最大）で人数推定、2500点サンプル×5回の中央値で安定化 → スペクトルクラスタリング → 全体をk-means。**教訓: 合成TTSは声がきれいすぎて検証にならない。必ず実録音で確認する**
- **句読点**: Whisper large-v3は日本語で句読点をほぼ付けない（実会議で6.1万字に「。」198個）。文脈継続＋お手本プロンプトでも不安定だったため、単語タイムスタンプの間と文末表現によるルールベース推定を追加。LLMは遅すぎる（6万字で数十分）ので使わない
- **字幕**: 校正・手修正・人名統一はテキストだけを変えるため、difflibで新テキストを元の単語タイミングに対応付け直してから分割（`_aligned_words`）
- **声紋ファイル名 = 人物名**。Windowsで使えない文字 `\/:*?"<>|` を含む名前は登録時に拒否
- **VRAMの受け渡し**: Whisper/ECAPA → LLM の順に処理し、LLM前に `transcriber.unload()` `diarization.unload()`、文字起こし前に `llm.unload_ollama()`
- **kotoba-whisper-v2.2 の評価（2026-09-28, ユーザー要望）**: v2.2 = kotoba-whisper-v2.0（ASR）＋ pyannote系の話者分離 ＋ punctuators（句読点）。実会議の抜粋で比較した結果:
  - ASR（v2.0-faster）: large-v3 より明らかに劣る（4分で939字 vs 1296字、文の脱落・誤認識が多い、句読点なし）。10倍速いが不採用。`condition_on_previous_text=True` だとほぼ全部を落とす、`word_timestamps=True` でctranslate2がネイティブクラッシュ（軽量化で層が少ないため）
  - punctuators（pcs_47lang）: 「間」を見ないため文の途中に「。」を打つ（「成功しました。とか言ってましたよね」）。自前のルールベース（間＋文末表現）のほうが自然 → 不採用
  - 話者分離: **pyannote を採用**（WhisperXと同じエンジン）。`pyannote/speaker-diarization-community-1`、`exclusive_speaker_diarization` を単語割り当てに使用。声紋照合は各話者の長い発話からECAPA声紋を作って既存の声紋DBと照合（声紋DBはECAPAで統一）
  - pyannote.audio 4.0.7 は torch を置き換えずに入った（cu130版のまま）。音声はtorchcodecを使わず波形テンソルで渡す
- **Whisperが遅い原因（2026-09-28調査）**: GPU使用率は91%で、GPUが遊んでいるわけではない。原因は (1) faster-whisper標準は30秒区間を1つずつ逐次デコードし小さな行列演算を繰り返す (2) beam_size=5 がbeam 1の約2倍 (3) ctranslate2 4.7.1 はBlackwell(sm_120)でint8 GEMMが `CUBLAS_STATUS_NOT_SUPPORTED`（int8_float16不可）。実会議4分×2の実測:
  | 方式 | 時間 | 速さ | 文字数 |
  |---|---|---|---|
  | 逐次・beam5（精度優先） | 232秒 | 1× | 2598 |
  | 逐次・beam1（バランス） | 98秒 | 2.4× | 2470（-5%） |
  | BatchedInferencePipeline x16・chunk15（高速） | 29秒 | 8× | 2210（-15%） |
  - 一括処理では initial_prompt（句読点のお手本）とホットワードで文字数が半減・不安定になるため、高速モードでは使わない
  - 一括処理は単語タイムスタンプが無音を取り込んで伸びる（「はい、」が1.5秒など）→ `transcriber._unstretch` で開始時刻を補正。それでも句読点・話者境界は精度優先より粗い
  - 一括処理は日本語の文の切れ目を空白で出す → `punctuate.py` で「。」に変換
- **HFトークン**は `settings.yaml` の `diarization.hf_token`（.gitignore済み）。設定タブから変更可。無い／失敗時は自前方式に自動で切り替え
- **CUDA版PyTorch**: PyPI版はCPU専用。RTX 50系(Blackwell)は cu128 以降が必要で、cu130 を使用
- **4h会議でAI処理が全部スキップされた件（2026-09-28）**: 文字起こし完了後、校正の1回目がCUDA OOM、以降の再試行・議事録・要約がすべて `std::bad_alloc`（RAM不足。Ollamaのロード時点で空きRAM 8.2GB）でllama-serverごと落ちた。文字起こしは保存済みで、`meta.json` の errors に3件のスキップが残る。画面上は止まったように見えるが、ジョブは終わっている
  - 12bへの切り替えが動かなかった原因: `_is_resource_error` が `bad_alloc` を判定していなかった → 追加して修正
  - 回復手順: アプリを再起動 → 履歴からジョブを開く → 「🔁 議事録・要約を作り直す」（文字起こしは再実行しない）
  - **未解決**: Ollama 0.34.4 の llama-server は、リクエストの `num_gpu` にかかわらず毎回 `-ngl 99` で起動していた（server.log の起動コマンドで確認）。VRAM不足時に層を減らす再試行（48→40→24）は効いていない
- **作業を3段階に分けた（2026-09-28、ユーザー指示）**: 「文字起こし→校正→議事録→要約」を1回で流すと、確認・修正を挟めず、4h会議では校正だけで数時間待たされた
  - ① `run_batch`: 文字起こし＋話者識別だけ（LLMは使わない）
  - ② 確認・修正: 話者名の表・発言修正の表（手修正した発言は `human=True` で AI校正の対象外）＋「✍️ AI校正」`proofread_job`。校正は約2500字ごとに保存し、`proofread` 済みを飛ばすので途中で止まっても続きから再開。進捗に残り時間を表示
  - ③ 「📋 議事録を作る」`make_minutes` / 「💡 要約と考察を作る」`make_insights`: ②で直した後の発言から作る。ルートの `議事録テンプレート.md` をプロンプトに入れて形を合わせる（書き換えれば形を変えられる）
  - 旧「🔁 議事録・要約を作り直す」と、①の「AI校正/議事録/要約」チェックは廃止
- **LLMが7倍遅くなる件（2026-09-28）**: アプリ本体(python)が文字起こし・話者識別の後もVRAMを約2GB持ったまま（unload＋empty_cacheでも解放されない。CUDAの作業領域とctranslate2の分と思われる）。gemma 31B(13.4GB)が0.8GBあふれて共有メモリに乗り、生成が25→3.7 tok/s、校正1回が約9分に。**対処: ①の後にアプリを再起動してから②③を行う**。根本対策（①を別プロセスで動かす）は未着手
- **文が語の途中で割れる・句読点がおかしい件（2026-09-28、4h会議の実データで調査）**
  - 主因1: 話者を単語（語の切れ端）ごとに決めていたため、話者の境目が語の途中に来て「こから出て／るんですか？」のように割れていた（文の途中で切れた342か所中310か所）→ `utterances._vote_phrase_speakers` で句読点・0.3秒の間で区切ったまとまりごとに多数決（1.5秒以上続く別話者だけ残す）
  - 主因2: `punctuate.py` が語の途中にも句読点を入れていた（「ワ、ークスペース」「エ。ージェント」）→ `inside_word`（カタカナ同士・「ー」や小書き文字の前・数字の途中）では付けない
  - 主因3: Whisperが語の頭の1〜2文字だけ数秒前の時刻を付ける（「エ」…9秒…「ビデンス」、「こ」…4秒…「っちが」）→ `punctuate.glue_word_heads` で続きの直前に寄せる。ひらがな・漢字の頭は janome（形態素解析）で同じ語か判定（requirements に追加。未導入なら判定を省く）
  - 「〜けど。」「〜ので。」（句点の約2割）→ 文をつなぐ表現は1.5秒未満の間なら「、」。読点の間の閾値 0.35→0.5秒
  - **学習済み修正が「。」→「、」を覚えて自動適用状態（3回）だった**。次の文字起こしから全句点が読点になるところだった → `glossary._learnable` で句読点を含む・1文字の置換は学習も適用もしない（既存の learned_words.yaml は消さずに無視）
  - 「ー番」→「一番」: `utterances.fix_ichi`（前がカタカナなら伸ばし棒として残す）
  - 過去の結果は「✂️ 文の区切り・句読点を整え直す」で作り直せる（GPU不要・0.5秒）。文字は単語データから作り直すため、AI校正・手修正済みの結果では警告を出し、2回押した時だけ実行

## 2026-10-04（WBミートアップ 2時間で調査）
- **文字起こしが38分抜けた件**: 1:25:21〜2:03:29 に文字が1つも無かった。ハルシネーション除外は0件で、アプリ側では何も消していない
